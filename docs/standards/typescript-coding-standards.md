# TypeScript coding standards

Condensed English version of the team's document `typescript-coding-standards.pdf` (version 1.0, Hebrew). Section numbers match the original so a rule can be traced back. If this file and the original disagree, the original wins.

The PDF stops after section 18. Its table of contents also lists section 19 (code review checklist), section 20, appendices A and B and a glossary, which were missing when this was written. Until they arrive, the 8 rules in section 17.3 are the critical set.

## 1. Scope and levels

Applies to all new TypeScript (`.ts`, `.tsx`, `.mts`, `.cts`) in frontend, backend, scripts, config files and tests, and to existing code that is refactored, within the change. It does not apply to `node_modules`, to generated code (Prisma client in `src/generated/`, OpenAPI or GraphQL codegen: change the source, never edit the output) or to external `.d.ts` files.

| Level | Meaning |
| --- | --- |
| MUST | Required. Code that breaks it is not approved. |
| MUST NOT | Forbidden. An exception needs lead approval and a code comment. |
| SHOULD | The default. Deviate only with a real reason. |
| MAY | A legitimate option. |

Exceptions (1.6): a comment saying why (not what), and a targeted suppression with a reason, for example `// eslint-disable-next-line @typescript-eslint/no-explicit-any -- the SDK has no types; validated in parseWebhook`. A file-wide `/* eslint-disable */` is forbidden.

## 2. General principles

- Clear beats clever. An explicit contract type beats a recursive generic (use `type UserUpdate = { readonly displayName?: string }`, not `DeepPartial<User>`).
- No abstraction for an imagined future case. Abstract when two real implementations exist.
- One reason to change per module, class and function. If the description needs "and", split it.
- One dependency direction: `Controller/Route -> Service -> Repository -> DB or external API`.
  - Controller: parse the request, validate input, turn the result into an HTTP answer. No business logic or queries.
  - Service: business logic and coordination. It MUST NOT know `Request` or `Response` (it takes typed values: `createLoan(input: CreateLoanInput)`).
  - Repository: data access and mapping. No business rules.
- New code matches the surrounding code: names, folders, error handling, import patterns. Consistency beats personal preference.
- SHOULD prefer composition (injected dependencies, functions) over inheritance.
- SHOULD treat data as immutable: create a new value instead of changing one.

## 3. Types

- 3.1 MUST NOT use wrapper types `String`, `Number`, `Boolean`, `Object` (use `string`, `number`, `boolean`). `bigint` is allowed; never mix `bigint` and `number` in one calculation.
- 3.2 `type` is the default for data (Props, DTOs, models). `interface` is for a behavioral contract that a class implements, or a public library API that consumers extend. MUST NOT define the same name as both. One convention per repo.
- 3.3 MUST write explicit types for: return values of exported functions; function parameters (except callbacks whose type comes from context); data crossing a layer boundary (DTO, API contract, Props). MUST NOT annotate when inference is obvious (`const count = 0`).
- 3.4 `any` is forbidden in new code. Exceptions only: an untyped library whose value is validated right away, or generic infrastructure code that does not leak `any` outward. Targeted suppression plus reason.
- 3.5 MUST use `unknown` for any external value that is not yet validated, and narrow before use. The `catch` variable is `unknown`.
- 3.6 SHOULD use a union for a closed set of states instead of several booleans (`{ status: 'idle' } | { status: 'loading' } | ...`). Intersections may combine contracts but MUST NOT have conflicting fields (that gives `never`).
- 3.7 SHOULD use literal types for a small closed set. MUST use `as const` for arrays and objects that are the source of truth, and derive the type from them: `type X = (typeof XS)[number]`.
- 3.8 SHOULD NOT use a regular `enum`. Use an `as const` object with a derived union, or a string union. MUST NOT use `const enum`. Enums generated by a tool (Prisma) may be used: import them, never copy them.
- 3.9 Use generics when the input type determines the output type. MUST constrain with `extends` when a property is needed. MUST NOT use a generic that appears once in the signature. Give meaningful names when there are several: `TItem`, `TResult`, `TError`.
- 3.10 MUST NOT annotate a callback parameter that is typed by context (`books.map((book) => book.title)`). SHOULD define a named callback type in public contracts. MUST NOT use the `Function` type.
- 3.11 One array syntax per repo (`@typescript-eslint/array-type`): `T[]` for simple types, `Array<T>` for complex ones. MUST NOT use `object` or `{}` as general types: use `Record<string, unknown>`. Use `Record` for a known key set (the compiler enforces full coverage) and `Map`/`Set` for dynamic keys. Prefer labeled tuples (`readonly [start: number, end: number]`). Create arrays and objects with literals (`[]`, `{}`), not `new Array()`/`new Object()`; use `push`, not index assignment.
- 3.12 One convention for "no value". `undefined` means not provided (optional field). `null` means present and intentionally empty (mainly from the DB). MUST NOT declare `field?: string | null` unless all three states have different meaning. Convert `null` to `undefined` at the layer boundary (`row.nickname ?? undefined`). With `exactOptionalPropertyTypes`, `x?: string` and `x: string | undefined` are different: do not pass `undefined` to an optional key, leave it out.
- 3.13 SHOULD mark `readonly` on model and DTO fields and on array parameters the function must not change. `readonly` is a compile-time check only; use `Object.freeze` when runtime protection is needed.
- 3.14 SHOULD use discriminated unions for states with variants. The discriminant MUST be a literal field with the same name in every variant. MUST check exhaustiveness with `never`: `default: return assertNever(x)`.
- 3.15 SHOULD narrow with built-ins first (`typeof`, `instanceof`, `in`, `Array.isArray`, literal compare). Custom type guards (`value is T`) are allowed, but a manual guard is an unchecked promise: for external data MUST validate with a schema (section 8) instead. Assertion functions (`asserts value is T`) MUST be `function` declarations.
- 3.16 MUST NOT use `as T` to silence a compile error. Allowed: `as const`; a DOM event target (`(event.target as HTMLInputElement).value`); `as unknown as T` for a partial mock in tests, with a reason. `as any` is forbidden everywhere. SHOULD prefer `satisfies` to check a value against a contract without widening it.
- 3.17 MUST NOT use the non-null assertion `!` in production code. Handle the missing case explicitly. Allowed in tests only (`no-non-null-assertion` on, tests excepted).
- 3.18 Errors: define custom classes that extend `Error`; type the `catch` variable `unknown` and narrow; never type an error as `any`.
- 3.19 SHOULD use a `Result<TValue, TError>` type for expected failures (validation, not found, a business rule) and `throw` for exceptional ones (infrastructure faults). Do not mix the two in one layer without a rule. Recommended rule: the Service returns `Result` for business failures and throws for infrastructure faults; the Controller maps both to the HTTP answer.

## 4. Compiler settings

`tsconfig.json` is part of the standard, not a personal choice. Production code MUST pass `tsc --noEmit` with no errors before merge.

| Flag | Level |
| --- | --- |
| `strict` (includes `noImplicitAny`, `strictNullChecks`, `strictFunctionTypes`, `useUnknownInCatchVariables`). Never turn it off. | MUST |
| `noImplicitReturns`, `noFallthroughCasesInSwitch`, `forceConsistentCasingInFileNames` | MUST |
| `isolatedModules` (in a project with a bundler) | MUST |
| `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` | SHOULD (strongly) |
| `noUnusedLocals`, `noUnusedParameters` (an `_` prefix opts out) | SHOULD |
| `verbatimModuleSyntax` | SHOULD |
| `skipLibCheck` | MAY |

- Match target, module and moduleResolution to the runtime; never copy them from another project. Node ESM: `NodeNext`. Bundler (Vite): `ESNext` plus `Bundler`.
- Set `lib` per environment. MUST NOT include `DOM` in server code.
- `sourceMap: true` in development. Backend production: SHOULD (readable stack traces). Never publish frontend source maps to the public if they expose source.
- SHOULD use a shared `tsconfig.base.json` with all strict flags, and have each package extend it and add only module, lib and jsx.
- Test files MUST NOT be in the build output. Strict flags MUST be the same for tests and production. `rootDir` and `outDir` are explicit.

## 5. Functions and methods

- 5.1 SHOULD use an arrow function assigned to `const` by default. Use `function` for: assertion functions, overloads, generators, methods inside a class or object. MUST use shorthand properties and methods in object literals (`{ title, describe: () => title }`).
- 5.2 Names are verb phrases. Fetch: `get` / `find` / `fetch`. Booleans: `is` / `has` / `can` / `should`. Change: `create` / `update` / `delete`. Convert: `to` / `map` / `parse`. SHOULD distinguish `get*` (returns or throws) from `find*` (returns `undefined` or `null`), consistently across the project. A name MUST NOT promise less than the function does.
- 5.3 MUST limit parameters to three; beyond that use one typed parameters object. SHOULD destructure an object parameter when using several fields. MUST NOT name a parameter `arguments`; use typed rest parameters.
- 5.4 MUST use default parameter syntax and MUST NOT mutate an argument. Parameters with defaults go last. A default applies to `undefined` only, not `null`.
- 5.5 SHOULD keep business logic in pure functions (same input, same output, no outside effect) and separate calculation from action. MUST inject non-deterministic dependencies (current time, random ids, network) instead of using them directly in logic.
- 5.6 Exported functions MUST have an explicit return type. Use `void` for no value and `never` for a function that never finishes. MUST NOT return `any` or a wide union such as `boolean | number | string`.
- 5.7 An `async` function returns an explicitly typed `Promise<T>`. MUST NOT mix `await` with `.then()` in one function. MUST NOT wrap promise-returning code in `new Promise`.
- 5.8 Every function does one of three things with an error: handles it, rethrows it with a new meaning, or returns a `Result`. MUST NOT catch an error and ignore it.
- 5.9 SHOULD be shorter than 40 lines with one level of abstraction; nesting at most three levels; use early return instead of `else`.
- 5.10 MUST NOT use `new Function` or `eval`. Event handlers take a typed event parameter (`React.ChangeEvent<HTMLInputElement>`), never the global `event`. SHOULD use `currentTarget` rather than `target` when you need the element the listener is on.

## 6. Classes, interfaces and objects

- 6.1 Data only: `type` and an object literal. Logic with no state: exported functions in a module. State plus several operations: a class. Several swappable implementations: `interface` plus classes. MUST NOT create a class that only wraps static functions: that is a module.
- 6.2 Internal state MUST be `private` or `#private`, and the public surface minimal. TypeScript `private` is compile-time only; `#field` is real runtime privacy. SHOULD use `#` when privacy is a security requirement. MUST NOT return a reference to a mutable internal structure: return a copy or a `readonly` type.
- 6.3 `public` is never written. `readonly` is required on every field that does not change after construction. `protected` only for intentional, documented inheritance. Member order: static fields, instance fields, constructor, public methods, private methods.
- 6.4 SHOULD use parameter properties (`constructor(private readonly repo: Repo) {}`). MUST NOT do heavy work or I/O in a constructor; use an async static factory.
- 6.5 Abstract classes only when close variants share implementation. Prefer `interface` plus composition. MUST NOT use an abstract class as a helper-function holder.
- 6.6 SHOULD write `implements` explicitly. The `interface` MUST be defined in the layer that consumes it (dependency inversion), not in the implementation layer.
- 6.7 MUST NOT go more than two inheritance levels without lead approval. MUST NOT inherit only to reuse code.
- 6.8 SOLID in practice: S = section 2.3; O = discriminated union plus `assertNever`, or injected behavior; L = an implementation must not narrow behavior or throw where the contract allows; I = several narrow interfaces (a function asks for `Pick<Repo, 'findOverdue'>`); D = depend on an interface, not a concrete class.

## 7. null, undefined and errors

- 7.1 With `strictNullChecks`, every path that can hold `null` or `undefined` MUST handle it explicitly. MUST NOT bypass with `!` or `as`.
- 7.2 Booleans may use shorthand (`if (isActive)`). MUST NOT use truthiness for strings or numbers: `if (name)` is forbidden; write `name !== undefined && name !== ''`, `items.length > 0`. MUST use `===` and `!==`. The only allowed exception is `value == null` (checks both), with a short comment, or a double check.
- 7.3 SHOULD use `?.` and `??`. MUST NOT use `||` for defaults of numbers, strings or booleans (it turns `0`, `''`, `false` into the default); use `??`. MUST NOT use `?.` as a replacement for error handling (`data?.items?.[0]?.name` hides real problems), and MUST NOT use `?.` on a value whose type is not optional.
- 7.4 MUST throw only objects that extend `Error` (`throw new NotFoundError('Book', id)`, never a string or a plain object). Catch only where you can do something meaningful: handle, add context and rethrow, or turn into a client answer. SHOULD keep the original with `{ cause: error }`.
- 7.5 MUST define a shallow error hierarchy with one base class per app, for example `AppError` with `code` and `httpStatus`, and subclasses (`ValidationError` 400, `NotFoundError` 404, ...). The central error handler maps `AppError` to an HTTP response and any other error to 500 with a generic message.
- 7.6 MUST NOT leave an empty `catch`, or one that only logs and carries on as if all is well. A deliberate ignore MUST be commented and logged (`logger.warn(...)`).
- 7.7 Every value crossing the system boundary is `unknown` until validated. A type declared on external data is an assumption, not a fact (section 8).

## 8. External data and runtime validation

TypeScript checks types at compile time only. At runtime nothing is left. A type on external data is the developer's promise, not the system's guarantee.

- 8.1 MUST validate every value that crosses the system boundary, at the entry point, once. `const books = (await res.json()) as Book[]` is forbidden.
- 8.2 What must be validated: external API responses (full schema); request body, query, params, headers (validate and normalize); environment variables (at startup); JSON and config files; DB raw query results (and rows with `null` fields, via a mapping); webhooks (verify signature and schema); `localStorage`, cookies, URL parameters; queue messages (validate and version).
- 8.3 MUST use a validation library that derives the TypeScript type from the schema, so there is one source of truth (here: Zod). `export type Book = z.infer<typeof bookSchema>`. MUST NOT write a type by hand and a separate schema next to it.
- 8.4 SHOULD use the non-throwing form (`safeParse`) where failure is expected, and turn it into a `Result` or an HTTP 400. MUST NOT return a raw validation error that exposes internal structure to an external client.
- 8.5 MUST validate all environment variables in one module, at process start, and export a typed config object. MUST NOT read `process.env` anywhere else. The process fails fast when a needed variable is missing. MUST NOT log the config object.
- 8.6 MUST keep three representations apart and MUST NOT return a DB record straight to the client: DTO / wire model (`CreateBookRequest`, `BookResponse`), domain model (`Book`), view model (`BookCardProps`). Use explicit mapper functions so adding a field to a model never leaks it (`passwordHash`, `internalNotes`).
- 8.7 With an ORM such as Prisma: the type reflects the schema at generate time, not the live DB. `null` columns need an explicit mapping to the `undefined` convention (3.12). A raw query returns an unvalidated value, so validate the result.
- 8.8 MUST NOT use a type assertion instead of validation: `JSON.parse(x) as AppConfig`, `request.body as Payload` and `jwt.decode(token) as Claims` are forbidden. Use a schema; for tokens use `jwt.verify` and then a schema (`decode` does not check the signature).

## 9. Modules and imports

- 9.1 MUST use ES modules (`import`/`export`). MUST NOT use `require` or `module.exports` in new TypeScript. In a Node ESM project (`moduleResolution: NodeNext`), relative imports MUST include the `.js` extension.
- 9.2 SHOULD prefer named exports over default exports (a default export loses its name in rename and refactor, lets each importer pick a different name, and auto-import is less reliable). A default export is allowed where a framework requires it (a route component, a config file). Put all `import` statements at the top of the file. Import from a given path in one statement. MUST NOT export a mutable binding (`export let`); export accessor functions instead. Export `const` only.
- 9.3 SHOULD NOT use `import * as X from`: it blocks tree shaking and hides unused code. Allowed when really needed (for example a CommonJS module such as `node:fs`).
- 9.4 MUST use `import type` for imports used only as types.
- 9.5 SHOULD organize by feature, not by technical type. One topic per file; about 300 lines is a warning sign, not a ban.
- 9.6 MUST NOT create circular dependencies. Prevent them with one dependency direction between layers, shared types extracted to a neutral module, `import type` for type-only dependencies, and the `import/no-cycle` lint rule.
- 9.7 A barrel file (`index.ts`) MAY be the public API of one feature. MUST NOT use a barrel at `src/` root, and MUST NOT import through a barrel inside the same feature. The barrel exports only the narrow public surface.
- 9.8 Each feature decides what it exposes. MUST NOT import another feature's internal file directly; import its `index.ts`. Enforce with `no-restricted-imports`.
- 9.9 One import-path convention per project, declared in `tsconfig`. Relative imports (`./`, `../`) inside one feature; an alias for crossing a feature boundary. MUST NOT chain more than two levels (`../../..`). An alias MUST also exist at runtime or in the bundler, or compiled code fails at runtime.

## 10. Naming and formatting

| Thing | Convention | Example |
| --- | --- | --- |
| Folder | kebab-case | `book-loans/` |
| Code file | kebab-case plus role | `book.service.ts`, `auth.middleware.ts` |
| React component file | PascalCase | `BookCard.tsx` |
| Test file | name of the tested file plus `.test.ts` | `book.service.test.ts` |
| Variable | camelCase | `activeLoans` |
| Module-level constant | UPPER_SNAKE_CASE | `MAX_RETRIES` |
| Function | camelCase, starts with a verb | `calculateLateFee` |
| Class | PascalCase noun | `LoanService` |
| Interface / Type | PascalCase, no `I` prefix | `BookRepository`, `LoanStatus` |
| Constant object used as an enum | PascalCase name | `LOAN_STATUS` or `LoanStatus` (one choice for the project) |
| Generic | `T` plus a description | `TItem`, `TResult` |
| Boolean | `is` / `has` / `can` / `should` | `isOverdue` |
| Event handler | `handle` plus event | `handleSubmit` |
| Event prop | `on` plus event | `onSubmit` |
| Private field | camelCase with `#` or `private` | `#connection` |

- 10.2 UPPER_SNAKE_CASE is only for a real module-level constant: a primitive value known when the code is written. MUST NOT use it for a local variable, the result of a calculation, or the result of a function call (`const CURRENT_USER = await getUser()` is wrong; `const currentUser` is right).
- 10.3 MUST NOT repeat the object name in field names (`user.name`, not `user.userName`). MUST NOT use an `I` prefix for interfaces or a `T` prefix for types (generics aside). MUST NOT use unclear abbreviations (`usr`, `bk`, `tmp2`); `id`, `url`, `db`, `api` are fine. MUST NOT use generic names with no meaning (`data`, `info`, `obj`, `handle`, `process`, `manager`, `helper`, `utils`) as the only name of a file or class. SHOULD put the unit in the name when it is not obvious (`timeoutMs`, `fileSizeBytes`). SHOULD NOT suffix async functions with `Async`; `Promise<T>` already says it.
- 10.4 Prettier enforces these (not manual review): single quotes for strings; template literals only for interpolation or newlines, and instead of concatenation; never split a long string with `+` across lines; no leading commas; trailing commas in multi-line structures; semicolons; consistent line breaks in multi-line arrays, objects and imports; dot notation for a known property (brackets only for a dynamic key); `**` instead of `Math.pow`; no nested ternary; no redundant ternary (`x ? true : false`).
- 10.5 MUST convert with `String(x)`, `Number(x)`, `Boolean(x)`, `parseInt(x, 10)`. MUST NOT use `new String(...)`, `new Number(...)`, `new Boolean(...)`, or tricks like `+value` or `value + ''`. MUST check the result of a number conversion (`Number('abc')` is `NaN`, typed as `number`): `if (Number.isNaN(parsed)) throw ...`. SHOULD convert external input in the validation layer (`z.coerce.number()`), not scattered through the code.

## 11. Collections and data

- 11.1 MUST use higher-order functions instead of manual loops, chosen by intent: `map` (convert), `filter`, `reduce` (aggregate), `find`/`findIndex`, `some`, `every`. `forEach` only for side effects (never to build a value with an outside variable).
- 11.2 `for...of` is right for: early exit (`break`), sequential async work (`for await`/`await` in the loop), very large collections where intermediate arrays are a measured problem, and iterating `Map`/`Set`/iterators. MUST NOT use `for...in` on arrays. Use `Object.keys`/`values`/`entries` for objects. `Object.keys(obj)` is typed `string[]`; do not cast it to `(keyof T)[]` without checking the object's real source.
- 11.3 MUST NOT mutate by accident. `sort` and `reverse` change the original: copy first (`[...books].sort(...)`) or use `toSorted` where supported. Other mutating methods: `splice`, `push`, `pop`, `shift`, `unshift`, `fill`, `copyWithin`. Use spread instead of `Object.assign` onto the original. Spread is a shallow copy; use `structuredClone` for a deep one. SHOULD type array parameters `readonly T[]`.
- 11.4 MUST handle the empty case explicitly: `books[0]` can be `undefined`. `reduce` without an initial value throws on an empty array, so MUST pass one. MAY use a non-empty tuple type (`readonly [TItem, ...TItem[]]`) when it is part of the contract.
- 11.5 SHOULD merge passes on large collections but MUST NOT give up readability on small ones. MUST NOT nest a search (`books.find` inside `loans.map` is O(n*m)); MUST build a `Map` for repeated lookups.

## 12. Asynchronous code

- 12.1 MUST prefer `async`/`await` to `.then()` chains, and MUST NOT mix them in one function. MUST NOT wrap code that already returns a Promise in `new Promise`. `new Promise` is only to wrap a callback-based API.
- 12.2 MUST NOT leave a floating Promise (`@typescript-eslint/no-floating-promises` and `no-misused-promises` on). Either `await` it, or run it on purpose in the background with explicit handling: `void send(...).catch((error: unknown) => logger.error(...))`. The request boundary has an async error handler (Express 5 handles `async` handlers).
- 12.3 `Promise.all` when every operation must succeed (one failure rejects all; the others keep running in the background). `Promise.allSettled` when each result matters on its own. `Promise.race` for timeouts. `Promise.any` when one success is enough.
- 12.4 MUST NOT run independent operations one after another in a loop; use `Promise.all(ids.map(...))`. MUST NOT use `forEach` with an async callback (it ignores the returned Promise). MUST limit concurrency when the number of operations is large or unbounded; work in batches.
- 12.5 MUST handle a late result arriving after state changed: in UI use `AbortController` in the effect cleanup and ignore `AbortError`; on the server run read-modify-write in a transaction or with optimistic locking, not as separate queries.
- 12.6 SHOULD pass an `AbortSignal` through functions that do long I/O and respect it. MUST cancel requests whose result is no longer relevant (navigation, a new search, a component unmounting).
- 12.7 MUST NOT `await` a value that is not a Promise. MUST NOT `return await` outside a `try` (inside `try/catch` it is needed so the `catch` runs).
- 12.8 Exported async functions MUST have an explicit `Promise<T>`. SHOULD combine with `Result`: `Promise<Result<Loan, BorrowError>>`. MUST NOT return `Promise<any>`, or `Promise<void>` when there is a meaningful result.

## 13. Documentation and comments

- 13.1 A comment explains why, never what. The type and the code say what.
- 13.2 MUST document: a non-obvious decision or workaround (with a link to the cause); assumptions about external systems that the types cannot express; a non-trivial algorithm or performance consideration; every lint suppression or exception to the standard. MUST NOT document obvious code, what the type already says, or dead code (delete it; git is the archive).
- 13.3 MUST write JSDoc on the public API of a module or library (exported functions, public classes, exported types used by outside consumers). MUST NOT repeat type information in JSDoc, and MUST NOT put types in `@param {string}`. SHOULD use `@deprecated` with the replacement.
- 13.4 MUST NOT leave a comment that no longer matches the code; update or delete it in the same change. Format for open tasks: `// TODO(ticket): description`. MUST NOT leave a `TODO` without context and an owner.
- 13.5 SHOULD give each feature a short `README.md` (responsibility, public API, dependencies). A public REST/GraphQL API MUST be documented in a machine format (OpenAPI), SHOULD be generated from the schemas of section 8 so it cannot drift from the code.

## 14. Tests

- 14.1 Unit tests MUST cover business logic, calculations and edge cases. Integration tests MUST cover critical flows and the data layer. End-to-end tests SHOULD cover the main business paths only. Type tests SHOULD cover generic and infrastructure types (`expectTypeOf`). Every bug fix MUST come with a test that fails before the fix and passes after.
- 14.2 `tsc --noEmit` is a mandatory CI step. SHOULD use `// @ts-expect-error` to check that bad code really fails to compile. MUST NOT use `@ts-ignore`.
- 14.3 MUST cover: empty array, empty object, empty string; `null` and `undefined` in every optional parameter; boundary values (0, a negative number, a boundary date, a maximum); error paths (assert the specific error, not just "an error"); invalid external input (missing field, wrong type, extra field, malformed JSON); async failure, timeout and cancel.
- 14.4 MUST use Arrange, Act, Assert with visual separation. The test name describes the behavior and expected result, not the function name. One behavior per test. MUST NOT put conditional logic (`if`, loops) in a test; use `it.each`.
- 14.5 MUST test behavior, not internal implementation (not `toHaveBeenCalledTimes` on internals). MUST NOT write tests that depend on run order or shared state, on real time (inject a clock or fake timers), on a real external network (mock at the HTTP level), or on an arbitrary `sleep` (wait for a condition). SHOULD use test data builders.
- 14.6 SHOULD put mocks at the system boundary (DB, HTTP, clock), not between internal modules. MUST type a mock against its contract. MUST NOT use `as any`; `as unknown as T` only with a reason.
- 14.7 SHOULD keep meaningful coverage of business logic. MUST NOT treat coverage percentage as a goal. Critical flows (payments, permissions, auth) MUST be fully covered, including failure paths.

## 15. Security

- 15.1 Types are not security: they are erased at compile time. Check permission at runtime on the server.
- 15.2 MUST separate authentication (who you are) from authorization (what you may do). MUST check authorization on the server, per request, per resource, against the resource owner (prevent IDOR: a logged-in user must not read any record by changing an id). MUST NOT rely on hiding things in the UI. MUST verify a token's signature (`verify`, not `decode`). Default is deny: a route with no explicit permission is blocked.
- 15.3 Validation (reject input that breaks the contract) is not encoding (fit a value to where it is written). MUST encode at the point of use: HTML (framework auto-escaping; MUST NOT use `innerHTML` with user input; MUST NOT use `dangerouslySetInnerHTML` without sanitization by a dedicated library and a security review); SQL (parameterized queries or the ORM; MUST NOT build SQL with string concatenation); shell (MUST NOT build a command from a string; pass arguments as an array); URL (`encodeURIComponent`); logs (strip newlines and control characters from user input).
- 15.4 MUST NOT put a secret in source: passwords, API keys, connection strings, signing keys. Secrets come from the environment or a secrets manager through the config module (8.5). `.env` is in `.gitignore`; only `.env.example` without real values is committed. A secret that reached Git is leaked: MUST be replaced, not just deleted from history. MUST NOT expose a secret to the client: anything with a public prefix such as `VITE_` is shipped to the browser.
- 15.5 MUST hash passwords with a dedicated slow function (bcrypt, argon2); MUST NOT store plain text or a fast hash. MUST compare secrets in constant time (`crypto.timingSafeEqual`). MUST NOT log passwords, tokens, card numbers or personal identifiers; log an explicit list of non-sensitive fields. SHOULD configure logger redaction as defense in depth.
- 15.6 The client gets a generic message and an error code; full details go to the log only. MUST NOT return a stack trace, SQL, or table names. Login failure messages MUST be uniform ("wrong username or password"), so users cannot be enumerated.
- 15.7 MUST make sure `NODE_ENV=production` in production. MUST NOT use a default value for a secret in code (`env.JWT_SECRET ?? 'dev-secret'` is an open door).
- 15.8 Prototype pollution: MUST NOT deep-merge external input naively. MUST validate with a strict schema that strips unknown keys (including `__proto__`) and use only the validated result. SHOULD use `Object.create(null)` or `Map` for dynamic dictionaries. MUST use `Object.hasOwn(obj, key)`, not `key in obj`, to test a key on external objects. MUST NOT write to a field named by an external key without an allow-list.
- 15.9 Dependencies: MUST run a vulnerability check (`npm audit` or equivalent) in CI and block merge on severe findings; commit the lockfile; check a new dependency before adding it (maintained, number of transitive dependencies, license, size); MUST NOT run install scripts of an unknown dependency in CI without checking. SHOULD automate security updates (Renovate or Dependabot) with tests that block regressions.

## 16. Performance

- 16.1 MUST measure before optimizing. MUST NOT hurt readability for an unmeasured gain. MUST fix algorithmic problems (complexity, N+1) even without measuring.
- 16.2 SHOULD avoid creating objects and functions inside hot loops or on every render. This is not a blanket rule: a small object is cheap and clarity matters more.
- 16.3 Complex types cost compile time and developer experience, not runtime. MUST NOT use deep recursive types or nested conditional types without a real need. SHOULD split a complex type into named intermediate types.
- 16.4 SHOULD avoid repeated copies of large structures. MUST NOT use `structuredClone` or `JSON.parse(JSON.stringify(...))` on large structures in hot paths (JSON also loses `Date`, `Map`, `Set` and `undefined`).
- 16.5 Data layer: MUST paginate every endpoint that returns a list; MUST prevent N+1 (one query with `include`/`JOIN`, or one batched `IN` query); SHOULD select only the fields needed; SHOULD stream large files instead of loading them into memory; MUST build a `Map` for repeated lookup.
- 16.6 SHOULD lazy-load heavy modules not needed at startup (`await import(...)`). Frontend: split by route, lazy-load images, virtualize long lists. MUST NOT add a dynamic import in a hot path that is not cached.
- 16.7 Priority order: correctness, then clarity, then performance. An optimization that hurts clarity MUST have a comment recording the measurement and the reason.

## 17. Tooling and automation

- 17.1 Every rule that can be enforced automatically MUST be. Code review is for design and correctness, not formatting.
- 17.2 Responsibilities: the TypeScript compiler (types, `strict`); ESLint with `typescript-eslint` type-aware (code rules, conventions); Prettier (formatting); the test framework (behavior). No overlap: use `eslint-config-prettier` so ESLint does not enforce formatting.
- 17.3 ESLint MUST use `typescript-eslint` with type-aware configuration (`strictTypeChecked` and `stylisticTypeChecked`, `parserOptions.projectService: true`) plus these rules, all set to `error` (a non-blocking warning piles up and is ignored):
  - `@typescript-eslint/no-explicit-any`
  - `@typescript-eslint/no-non-null-assertion`
  - `@typescript-eslint/no-floating-promises`
  - `@typescript-eslint/no-misused-promises`
  - `@typescript-eslint/explicit-module-boundary-types`
  - `@typescript-eslint/consistent-type-imports`
  - `@typescript-eslint/switch-exhaustiveness-check`
  - `eqeqeq: ['error', 'always', { null: 'ignore' }]`
- 17.4 One `.prettierrc` for the whole repo, committed. MUST NOT configure formatting at the personal IDE level. Settings: `singleQuote: true`, `semi: true`, `trailingComma: "all"`, `printWidth: 100`, `arrowParens: "always"`.
- 17.5 SHOULD run fast checks before commit on changed files only (`lint-staged`: `eslint --fix`, `prettier --write`). MUST NOT run the full test suite in a pre-commit hook. A hook can be skipped, so the CI is the real gate.
- 17.6 CI MUST run, and any failure MUST block merge: `npm ci`; `tsc --noEmit`; `eslint . --max-warnings=0`; `prettier --check .`; `npm test`; `npm audit --audit-level=high`; `npm run build`. `main` is protected: no direct push; pull request with approval and green checks. MUST NOT merge code with TypeScript errors, a new `@ts-ignore`, or skipped tests without a justification.
- 17.7 Optional tools: `knip`/`ts-prune` (dead code), `madge` or `import/no-cycle` (cycles), a bundle-size check, an error-monitoring service tied to source maps.

## 18. Additional decisions and recommendations

- 18.1 MUST use `@ts-expect-error` with a reason, never `@ts-ignore` (it keeps hiding the error after it is fixed).
- 18.2 MUST pin the TypeScript version exactly in `package.json` (no `~` or `^`). Upgrading is a dedicated pull request.
- 18.3 SHOULD use branded types for ids in systems with many ids of the same base type (`UserId`, `BookId`), so swapped arguments fail to compile. Skip it in small systems.
- 18.4 SHOULD inject a clock (`type Clock = { readonly now: () => Date }`) and MUST NOT call `new Date()` or `Date.now()` inside business logic.
- 18.5 MUST NOT use `console.log` in production code. MUST use a structured logger (JSON, levels, a correlation id per request, redaction of sensitive fields). The `no-console` rule is on, except in scripts.
- 18.6 SHOULD give every feature flag an owner and a removal date. MUST NOT leave code that only runs behind a permanently-off flag.
- 18.7 A change to a public contract (API, exported type, DB schema) MUST go through expand, migrate consumers, mark `@deprecated`, then remove. MUST NOT rename and remove in one change.
- 18.8 SHOULD share one `tsconfig.base.json` across the packages in a monorepo.
- 18.9 SHOULD enforce layer boundaries (2.4) and feature public APIs (9.8) with a tool (`no-restricted-imports`), not by discipline.
- 18.10 MUST store and transmit dates in UTC, ISO 8601, and convert to a local time zone in the presentation layer only. MUST NOT depend on the server's time zone. SHOULD distinguish an instant in time from a calendar date when both exist.

## Decisions for this project (D9, approved 14 October 2026)

These adjust or add to the original. They win over the text above for this repository.
